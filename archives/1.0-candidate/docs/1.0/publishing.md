# Publishing AI First 1.0

Generate the manifest from the same source records as the site, documentation,
or service registry. Do not maintain a second hand-written inventory when the
product already has stable identifiers, titles, revisions, languages, access
rules, and contract locations.

For a small site, keep items inline. For a large site, shard catalogs by real
selection dimensions and publish verified exhaustive bounds. Write children
first, recalculate their pins, then atomically replace the entry manifest. A
failed build must leave the previous complete publication usable.

Create full text and structured representations from one semantic source.
Preserve code, tables, restrictions, examples, and exact applicability. A
summary is additional convenience and cannot replace full content.

Filter protected descriptors, names, links, and errors before serialization for
the audience. A denied material response is too late if its name was already
disclosed in a public manifest. Credentials remain outside the publication and
reader logs. Isolate caches by principal and tenant.

Capability items point to existing contracts. Do not create a business endpoint,
duplicate an operation schema, or invoke an operation merely to satisfy AI First.
Use `external` with an explicit description when no supported static binding
exists. Report unverified runtime behavior as unknown or not-run.

Use the migration/export command in [migration.md](migration.md) for local,
preflight-first output. Browser publishers should configure MIME types, CORS,
cache validators, and the HTML or HTTP discovery declaration described by the
normative transport specification.
